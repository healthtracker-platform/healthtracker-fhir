The HealthTracker platform is presented as a distributed system composed of six components. Except for the mobile application, which will be installed on mobile devices, the other components will be deployed in the cloud. The cloud deployment will be carried out through the Heroku platform, except for the HL7 repository, which will be hosted on Azure. The interaction between components is identified in the figure through numbers. Values 1, 3, 4, and 5 will be interactions carried out through REST web services over HTTPS transport with data structured in JSON. Interaction number 2 (between the standardization service and the FHIR repository) will involve interactions using the FHIR standard. Finally, interaction number 6 will involve a connection to the database.

The following will explain the tasks of each component and their technological base.

-**Mobile application for the patient**: This is a hybrid mobile application, meaning a web application adapted to be packaged into an artifact that can be installed on mobile devices, both Android and iOS. For this, the Ionic framework is used, which allows the use of Angular + Angular Material for interface development and web clients. This component's task is to provide the patient with a place to enter daily measurements and send them to the standardization component for encoding and encapsulation in an appropriate format to be stored. Similarly, the patient’s mobile app can request data from the standardization component to display it to the patient.

-**Health panel for health care professionals**: This is a web application also developed with Angular + Angular Material and served by a Node.js + Express web server. It has the same functionalities as the mobile application for the patient, but in this case, the information sent to the standardization component is entered by the healthcare professionals.

-**User manager component**: This is a Spring Boot application that uses an embedded web server called Jetty, which allows working with synchronous data flows. It manages the users and roles needed in the project. Through Spring Security, it has an authentication filter configured that, upon receiving credentials via the HTTP Basic Authentication method, generates tokens following the JWT standard. Both the patient’s mobile application and the health professionals' panel will interact with this component to store users and identify them on the platform.
User manager database: Information regarding different user types is stored in a relational PostgreSQL database. Passwords will be  stored in hashed form.

-**Standardization component**: This is a Spring Boot application that uses an embedded web server called Netty to work with asynchronous data flows. It uses a project called HAPI-FHIR, a Java implementation of the FHIR standard, to transform data received from the mobile application and the health professionals' panel into standardized data via FHIR and encoded using the SNOMED CT ontology. Once this data has been processed, it is sent as a transaction-type bundle for storage in the HL7 FHIR repository. Similarly, when front-end applications need data, they call the standardization service, which first retrieves the data from the repository and decodes the information into the format required by the web application that requested the data. This component will have an authorization filter that will check the integrity and validity of the token associated with each request it receives. This component will store the key used to hash the token’s signature and will be able to independently confirm the authenticity of the token without consulting third-party components.

-**FHIR repository**: This is an instance of an implementation of the FHIR standard deployed in the cloud, provided by Azure with a persistence layer. This repository is responsible for receiving data in FHIR format and storing it. By using this repository, data exploitation by third parties is guaranteed in an interoperable way.
