La plataforma HealthTracker se presenta como un sistema distribuido compuesto por seis componentes, excepto la aplicación móvil que estará instalada en el móvil, los demás estarán desplegados en la nube. El despliegue en la nube se realizará a través de la plataforma Heroku, excepto el repositorio HL7 que estará alojado en Azure.
La interacción entre componentes está identificada en la figura a través de números. Los valores 1,3,4,5 serán interacciones que se realizarán a través de servicios web REST sobre transporte HTTPS con datos estructurados en JSON. La interacción número 2 (entre el servicio de estandarización y el repositorio FHIR) serán interacciones usando el estándar FHIR. Finalmente, la interacción número 6 comprenderá una conexión a base de datos.
 
A continuación, se procederá a explicar las tareas de cada componente y su base tecnológica.

- **Aplicación móvil paciente**: es una aplicación móvil híbrida, es decir, una aplicación web adaptada para ser empaquetada en un artefacto que se puede instalar en los dispositivos móviles, tanto Android como IOS. Para ello se usa el framework Ionic, que permite usar el Angular + Angular Material para el desarrollo de la interfaz y los clientes web. Este componente tendrá la tarea en proporcionar al paciente un lugar donde introducir las mediciones que vaya realizando día a día y enviarlas al componente de estandarización para su codificación y encapsulación en formato apropiado para, posteriormente, ser almacenadas. Del mismo modo la aplicación móvil del paciente podrá pedir datos al componente de estandarización para mostrarlos al paciente.

- **Panel de los profesionales de la salud**: es una aplicación web desarrollada también con Angular + Angular Material y servida por el servidor web Node.js + Express. Posee las mismas funcionalidades que la aplicación móvil del paciente, pero en este caso la información que se envía al componente de estandarización es introducida por los profesionales de la salud.

- **Componente de gestor de usuarios**: es una aplicación Spring Boot que utiiza el servidor web embebido denominado Jetty que permite trabajar con flujos de datos síncronos. Gestiona los usuarios y roles necesarios en el proyecto. A través de Spring Security posee configurado un filtro de autenticación que tras recibir las credenciales en base al método HTTP Basic Authentication genera tokens siguiendo el estándar JWT. Tanto la aplicación móvil del paciente como el panel de profesionales de la salud atacarán a este componente para guardar los usuarios e identificarlos en la plataforma. 
Base de datos del gestor de usuarios: la información relativa a los diferentes tipos de usuarios es almacenada en una base de datos relacional PosgreSQL. Las contraseñas se almacenarán en forma de hash.

- **Componente de estandarización**: es una aplicación Spring Boot que utiliza un servidor web embebido denominado Netty para trabajar con flujos de datos asíncronos. Hace uso de un proyecto denominado HAPI-FHIR, una implementación en Java del estándar FHIR para transformar los datos recibidos de la aplicación móvil y del panel de los profesionales de la salud en datos estandarizados mediante FHIR y codificados mediante la ontología SNOMED CT. Cuando estos datos han sido tratados se envían a modo de bundle de tipo transacción para el almacenamiento al repositorio de HL7 FHIR. Del mismo modo, cuando front-ends necesitan datos llaman al servicio de estandarización que, en primer lugar, recupera los datos del repositorio y decodifica la información en el formato requerido por la aplicación web que ha requerido los datos. Este componente poseerá un filtro de autorización que comprobará la integridad y validez del token asociado a cada petición que reciba. Este componente almacenará la clave con la que se hizo el hash de la firma del token y podrá confirmar la autenticidad del token de manera autónoma sin consultar a terceros componentes.

- **Repositorio HL7**: es una instancia de una implementación del estándar FHIR en desplegada en la nube que proporciona Azure con una capa de persistencia. Este repositorio se encarga de recibir datos en formato FHIR y almacenarlos. 	Con el uso de este repositorio se garantiza la explotación de los datos por parte de un tercero de un modo interoperable.
